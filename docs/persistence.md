# Persistence

The shipped provider stores corrected draft-v2 data beneath `hexagon/persistence/v3/<schema-id>`. If `hexagon/v2/<schema-id>` exists, startup logs `HEXAGON_PERSISTENCE_RESET` and leaves that legacy root untouched: it is never opened, migrated, modified, or deleted. `InMemoryPersistenceProvider` shares the transactional engine for deterministic tests; `FileSystemPersistenceProvider` consumes an injected storage adapter. Hexagon defines this protocol as a platform-whitelisted library. The standalone HL2RP game supplies the production OS adapter because the protocol deliberately depends on OS-level exclusive and atomic file operations; startup fails if the game cannot construct that adapter rather than downgrading those guarantees.

Documents are versioned envelopes with collection, key, revision, persisted-type ID/version, and concrete payload. Every type is registered explicitly. Repositories expose one canonical committed instance per address; unit-of-work editors deserialize isolated copies, and staged changes remain invisible until commit.

Initialization first acquires `lease.lock` for the provider lifetime. Production holds an OS `FileStream` opened with `FileShare.None` and write-through semantics, so a second process fails before it can read or mutate store files. Every commit is a separate immutable `wal/frames/{sequence}-{hash}.frame`, followed by `wal/acks/{sequence}.ack`. Frames and acknowledgements repeat store ID, writer epoch, compaction generation, sequence, and previous-ack hash. Both files are reread and verified before the committed view changes. The verified acknowledgement is the commit point; a later redundant commit-head write failure returns success with degraded health and must be repaired before another commit, checkpoint, or clean shutdown. Missing, corrupt, duplicated, or gapped acknowledged frames are fatal; only frames without an acknowledgement are recoverable orphans.

Immutable files are published absent-or-complete: the standalone game's adapter writes and flushes a same-directory staging file, then atomically renames it without overwrite. Abandoned `.staging` files are removed only after the exclusive lease is held.

Checkpoints are immutable content-addressed blobs with checksummed manifests and completion markers. Defaults checkpoint every 128 commits, retain two complete generations, trigger under 16 MiB soft WAL pressure, cap retained WAL at 64 MiB, cap a frame at 8 MiB, and cap retained history at 1,024 commits. A checkpoint is fully reread before pruning, and all frames required by the older fallback checkpoint remain. Tombstones are removed only by a verified checkpoint; this advances the compaction generation and makes older units of work fail with `StaleTransaction`.

`ShutdownAsync` is idempotent and returns durable/checkpoint sequences, clean versus recoverable status, the final checkpoint result, and lease-release status. A final checkpoint failure is degraded but recoverable when the acknowledged WAL remains intact.

The same schema-aware `IPersistenceInvariantSet` runs against a private candidate state during recovery and before every frame write. It requires exact current outer and nested payload types/versions, codec round-trips, exact item traits, declared reference categories and scene kinds, canonical keys, widened inventory geometry, reverse guards, reservations, locations, and relationship integrity. Only a completely validated recovery state is atomically published as `Ready`.

Every live character owns a `CharacterLifecycleGuardRecord`. `CharacterReferenceMutationService` stages reference and guard changes in the same unit of work, advancing guards for the union of old and new character targets. Direct reference writes without matching guard deltas fail commit invariants; character deletion removes the character, guard, owned graph, and matching references atomically. Item actions attach unchanged dependencies for every consulted character, guard, inventory, item, and placement plus an `InventoryAccessProof`; capability revisions are rechecked under the commit gate even for zero-mutation actions.

Schema configuration is stored as immutable `hexagon.config` documents in the `configuration` collection. `TypedConfigurationStore` rejects unknown keys, type changes, malformed codec payloads, and stale revisions. It creates missing defaults in one commit only after recovered domain validation succeeds. Runtime consumers read and update values through their registered typed definitions; configuration snapshots expose only stable type IDs, document revisions, and canonical encoded values for deterministic recovery evidence.
