# Persistence

The shipped provider stores corrected draft-v2 data beneath `hexagon/persistence/v3/<schema-id>`. If `hexagon/v2/<schema-id>` exists, startup logs `HEXAGON_PERSISTENCE_RESET` and leaves that legacy root untouched: it is never opened, migrated, modified, or deleted. `InMemoryPersistenceProvider` shares the transactional engine for deterministic tests; `FileSystemPersistenceProvider` consumes an injected storage adapter. Hexagon defines this protocol as a platform-whitelisted library. The HL2RP game supplies one whitelist-safe production adapter over the engine's `BaseFileSystem`, shared by every host shape — dedicated server, editor-hosted bootstrap, and standalone — so the streamed assembly passes s&box access control everywhere it runs.

Documents are versioned envelopes with collection, key, revision, persisted-type ID/version, and concrete payload. Every type is registered explicitly. Repositories expose one canonical committed instance per address; unit-of-work editors deserialize isolated copies, and staged changes remain invisible until commit.

Initialization first acquires `lease.lock` for the provider lifetime. Production holds the engine filesystem's write handle, which opens the physical backing file with no shared writer (Zio's `PhysicalFileSystem` default share), so a second provider — in this or any other process — fails at lease acquisition before it can mutate store files. Whitelist-safe code cannot flush past the operating-system cache, so durability against power loss is bounded by the OS cache; durability against process crashes is unchanged. Every commit is a separate immutable `wal/frames/{sequence}-{hash}.frame`, followed by `wal/acks/{sequence}.ack`. Frames and acknowledgements repeat store ID, writer epoch, compaction generation, sequence, and previous-ack hash. Both files are reread and verified before the committed view changes. The verified acknowledgement is the commit point; a later redundant commit-head write failure returns success with degraded health and must be repaired before another commit, checkpoint, or clean shutdown. Missing, corrupt, duplicated, or gapped acknowledged frames are fatal; only frames without an acknowledgement are recoverable orphans.

Immutable publication stages a same-directory `.staging` file, rereads and verifies it, then copies it to the final name with create-new semantics. No atomic rename is available to whitelist-safe code, so a crash inside the short copy window can leave one torn file at the final name — the torn-tail case recovery tolerates below. Abandoned `.staging` files are removed only after the exclusive lease is held.

Adapters that cannot finalize atomically may leave one torn file at its final name after a crash. Recovery tolerates exactly one torn *tail* artifact per WAL metadata class, each only in the exact state an interrupted write can produce, and logs the repair: an unreadable acknowledgement at exactly the durable tail + 1 with no commit head is discarded like an unacknowledged frame (`HEXAGON_TORN_TAIL_ACK_DISCARDED`; its frame is swept by the orphan pass and counted in `DiscardedUnacknowledgedFrames`); an unreadable commit head whose file name matches a verified acknowledgement is deleted and recreated from that acknowledgement (`HEXAGON_TORN_COMMIT_HEAD_RECREATED`); an unreadable checkpoint prune intent is discarded because its write-and-verify never completed, so no pruning began (`HEXAGON_TORN_PRUNE_INTENT_DISCARDED`) and the next checkpoint recomputes the prune. Every other corruption — including an unreadable acknowledgement referenced by a commit head or below the durable tail, a second torn artifact of the same class, or a torn head without its backing acknowledgement — remains fatal. Checkpoint artifacts that no verified generation references — a completion that failed verification, or a manifest or blob no valid completion names — are deleted once recovery has validated the store (`HEXAGON_INVALID_CHECKPOINT_ARTIFACTS_DISCARDED`): recovery already ignores them, so no recovered state changes, but a torn file left at its content-addressed final name would otherwise collide with every later checkpoint at that sequence.

Fatal corruption fails recovery closed by default; there is no automatic discard. An operator can arm the server ConVar `hexagon-persistence-quarantine` for one host start as a deliberate recovery: only if recovery then throws on genuine corruption — never on a tolerated torn tail, and never on an intact store — the still-held lease is kept while the unreadable WAL and checkpoint artifacts are archived under `quarantine/<writer-epoch>/` and a clean store is rebuilt at sequence zero (`HEXAGON_PERSISTENCE_QUARANTINED`, surfaced as `PersistenceHealth.RecoveredByQuarantine`). This accepts the resulting data loss; `format.json` and the lease are left in place so the store keeps its slot. The arming is consumed at the start of that host attempt regardless of outcome, so it cannot linger to quarantine a later store — re-arm to quarantine again. Three boundaries are deliberate. Quarantine rebuilds the whole store, so a readable checkpoint whose retained WAL chain is broken is archived (recoverable by hand under `quarantine/`) rather than partially salvaged. `format.json` corruption is preserved rather than self-healed: the manifest is checked before anything moves, and when it is the corrupt artifact quarantine is refused (`HEXAGON_PERSISTENCE_QUARANTINE_REFUSED`) with no WAL or checkpoint file archived, so that narrow class still fails closed. And quarantine covers only corruption found while reading the WAL and checkpoint artifacts; corruption detected when the recovered documents are applied to the schema — an unknown persisted type, a non-current type version, a payload that is not canonical, or a recovery invariant failure — is outside its scope: the artifacts are readable and the fault lies in the data model, so it fails closed even when armed.

Checkpoints are immutable content-addressed blobs with checksummed manifests and completion markers. Defaults checkpoint every 128 commits, retain two complete generations, trigger under 16 MiB soft WAL pressure, cap retained WAL at 64 MiB, cap a frame at 8 MiB, and cap retained history at 1,024 commits. A checkpoint is fully reread before pruning, and all frames required by the older fallback checkpoint remain. Tombstones are removed only by a verified checkpoint; this advances the compaction generation and makes older units of work fail with `StaleTransaction`. A verified checkpoint whose prune fails stays published and reports degraded health with `CheckpointRetryPending` (`HEXAGON_COMPACTION_DEGRADED`); the retained-WAL figure is re-measured from what actually remains, and the soft-pressure trigger backs off until the WAL grows by another soft threshold past that level, so a persistently undeletable file cannot force a fresh checkpoint generation on every commit — the commit-interval trigger, explicit checkpoints and the shutdown checkpoint still retry the prune, and the hard cap still bounds retained WAL. On restart a pending prune intent whose deletes fail again degrades recovery the same way (`HEXAGON_PRUNE_INTENT_DEGRADED`) instead of aborting it; corruption found while applying the intent still fails closed.

`ShutdownAsync` is idempotent and returns durable/checkpoint sequences, clean versus recoverable status, the final checkpoint result, and lease-release status. A final checkpoint failure is degraded but recoverable when the acknowledged WAL remains intact.

The same schema-aware `IPersistenceInvariantSet` runs against a private candidate state during recovery and before every frame write. It requires exact current outer and nested payload types/versions, codec round-trips, exact item traits, declared reference categories and scene kinds, canonical keys, widened inventory geometry, reverse guards, reservations, locations, and relationship integrity. Only a completely validated recovery state is atomically published as `Ready`.

Every live character owns a `CharacterLifecycleGuardRecord`. `CharacterReferenceMutationService` stages reference and guard changes in the same unit of work, advancing guards for the union of old and new character targets. Direct reference writes without matching guard deltas fail commit invariants; character deletion removes the character, guard, owned graph, and matching references atomically. Item actions attach unchanged dependencies for every consulted character, guard, inventory, item, and placement plus an `InventoryAccessProof`; capability revisions are rechecked under the commit gate even for zero-mutation actions.

Schema configuration is stored as immutable `hexagon.config` documents in the `configuration` collection. `TypedConfigurationStore` rejects unknown keys, type changes, malformed codec payloads, and stale revisions. It creates missing defaults in one commit only after recovered domain validation succeeds. Runtime consumers read and update values through their registered typed definitions; configuration snapshots expose only stable type IDs, document revisions, and canonical encoded values for deterministic recovery evidence.
